1 改善了什麼？為什麼體感差這麼多？

改之前（單一 warm）

一次 Edge 請求做完全部事，前端 await 到結束才重讀 Storage。

步驟大致成本
Yahoo 日 K中（1–3s）
最新基本面（估值／當月營收）快（多半吃 chip_raw_cache）

改之後（方案 1 拆分）

把「能先畫的」與「慢慢補的」切開。

階段做什麼額度

historyMOPS 12 月／12 季補齊不扣第二次

2 風險評估

風險 嚴重度 說明 現況緩解
history 不扣額度被濫用 中 已登入者可對「已存在但偏薄」的 fundamental/*.json 反覆打 history，燒 MOPS。 需 JWT；前端 session seal；滿檔 gap-driven 近乎 0 成本。長期可再加 history 額度或 token。
前後端版本不一致 高（部署時） 新前端送 phase，舊 Edge 忽略 → 每次都當 full 或行為不符。 DEV 已 volume-copy；prod 必須前端+Edge 一併上。
兩次 RTT / 兩次 invoke 低 core + history 比單次 full 多一次網路往返。 首屏仍較快；prefetch 用 progressive 可接受。
使用者只看到「最新一期」誤以為資料完整 中（產品） 先畫後補，表格會變長。 UI「歷史補齊中（月 n/12 · 獲利 m/12）」。
夜批與 on-demand 寫同一檔 低 兩邊都 merge 寫 fundamental/{ticker}.json。 gap-driven merge；最壞覆寫競爭，不是結構性毀損。
session seal 過嚴 中 core 封印後同 session 不再試；若 history 該補卻被跳過會卡住（見 §3）。 整頁 reload 清模組狀態；夜批兜底。

3 已發現的邏輯問題 / 潛在 BUG

BUG-A（中）— core 已封印時，頁面不再跑 history
StockDetailPage 只有在 core.ok && !core.fundamentalComplete 才呼叫 warmStockHistory。 若本 session 先前 prefetch / 日 K 已跑過 core，再次開頁時 warmStockCore 因 attemptedCore 直接回 FAILED（ok=false）， 即使 Storage 仍偏薄、history 其實可補，也不會進入 history。
建議修：core 封印但檔案仍 incomplete 時，仍允許 warmStockHistory；或 core seal 改回傳上次結果而非 FAILED。
BUG-B（低）— fundamentalSynced=0 時可能不重讀，但實際檔案已更新
syncFundamental 在 dataDate 已是最新時 skip，回傳 synced:0。 前端只在 fundamentalSynced > 0 || backfilled > 0 才 re-fetch。 多數情況 Storage 已 paint 過；若初讀 null、core 其實寫了檔但計數為 0（邊界），可能少讀一次。
實務上 write 成功會 +synced；skip 表示檔已存在。風險低。
注意-C（設計）— fundamentalHistoryLooksComplete 只看長度 ≥12
不檢查 gap。真正是否補完以 history 迴圈「回傳空」為準。core 階段的 complete 旗標可能偏樂觀（長度夠但有洞時極少見）。
已做對的部分
  • history / full 的 revenue→profit 必須串行（同檔互蓋）。
  • unknown ticker：跳過 MOPS，fundamentalComplete:true 封印，不燒額度迴圈。
  • history 無進度不 unseal，避免每開一次頁狂打 MOPS。
  • soft threshold（月<6 或無季）才 on-demand warm；6–11 交給夜批。
  • 日 K 只打 core，不再被 30s 歷史拖住。

9 本地測試檢查清單

  1. DEV Edge 已 volume-copy（目前已做）+ 本地 npm run dev 指到 DEV。
  2. 選一檔 Storage 沒有 fundamental/*.json 的代號。
  3. Network 應見兩次 stock-report：body 含 "phase":"core" 再 "history"。
  4. core 回應後 UI 應已有產業／估值／至少最新月或季。
  5. history 期間可操作畫面；表格列數增加；可出現「歷史補齊中」。
  6. 同 session 再開同一檔：不應再扣第二次 core 額度（封印）；確認是否仍需要修 BUG-A。
  7. 無 JWT 打 warm → 401；額度用盡 → 429。
