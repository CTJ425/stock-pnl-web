0. 一句話總覽

本系統是前端 SPA（GitHub Pages）+ Supabase（Auth／Postgres／Storage／Edge）。 即時報價與名單多半即時打外部；籌碼／基本面／日 K／總經則由 Edge 批次寫入 Storage，前端再直接下載 JSON（不耗 Edge 額度）。

OpenAPI openapi.twse.com.tw

證交所「機器可讀」REST。雲端 Edge 連線曾出現 Connection reset（0.6.52 已做軟取用／備援）。

非 OpenAPI 其他來源

TWSE rwd JSON、MIS 即時、MOPS 月報／季報、Yahoo 日 K／匯率、FRED 總經、TPEx OpenAPI。

Review 視角：「功能好不好」要拆成（1）來源穩不穩、（2）時序對不對、 （3）失敗時有沒有短路／沿用舊檔、（4）觀測（cron 60s vs Edge 110s）會不會騙人。

4. 資料時序（台北時間）

以 schema.sql 預設 cron 為準；正式區若用過 alter_job 以 DB 為準。UTC→台北 +8。

4.1 排程總表

jobname Cron（UTC） 台北時間（約） body action pg_net timeout
stock-report-nightly */15 8-15 * * 1-5 週一至五 16:00–23:45 每 15 分 generate-all（內部 chips→market-data→history，預算 ~110s） 60s ⚠️ 低於實際 chips+market
market-daily */15 7-10 * * 1-5 週一至五 15:00–18:45 每 15 分 sync-market 60s
source-probe */15 8-15 * * 1-5 16:00–23:45 每 15 分 probe 60s
macro-daily */30 12-18 * * * 每日 20:00–02:30 每 30 分（跨日） sync-macro 60s
fx-daily 0 3,9 * * * 每日 11:00、17:00 sync-fx 60s

4.2 交易日時間軸（示意）

08:30–09:00 / 13:25–13:30
MIS 試撮價；庫存若未標「試撮」可能誤導（AUDIT-01 已修前端標記）。
09:00–13:30 盤中
stock-price MIS 即時；前端 L1/L2 快取。不跑 generate-all（cron 從 16:00）。
15:00–18:45
market-daily：FMTQIK + BFI82U → market/daily.json；齊備後 reason=skipped 零外網。
16:00–23:45 每 15 分
generate-all：chips（T86／報告／TOP 軟更新）→ market-data（Yahoo 日線 + OpenAPI 基本面）→ history（MOPS）。 預算不足則 skip 後段，下輪再補（P1）。
同窗 source-probe
探測估值／借券來源是否變動，寫 source_probe_log，不寫使用者報告。
夜間–凌晨 macro；日中 fx
與台股 short-circuit 解耦，避免 decideSkip 擋掉總經／匯率。

4.3 手動更新（admin-run）時序

前端每個 job 各一次 HTTP（0.6.47+），進度條可看卡點。建議順序與夜班一致：

手動全部執行（示意） 1 generate-chips → OpenAPI TOP(軟) + rwd T86… ~數十秒 2 generate-market-data → Yahoo daily + OpenAPI 基本面 有檔則 skip Yahoo 3 generate-history → MOPS 一輪（不重打 TOP） 可 ~1–2 分 4 sync-market → rwd 全市場 常 skipped 5 sync-top-tickers → force 刷新 MI_INDEX20 可 RST→備援/舊檔 6 sync-macro / sync-fx / probe

7.2 仍存在或半開的風險（隱藏／架構）

嚴重度問題證據／影響建議
高 pg_net timeout_milliseconds=60000 ≪ 實際盤後 實測 chips ~59s、三 phase ~196s；cron 觀測常「假失敗」 拉到 180s+；或 cron 拆三 action
高 cron generate-all 單請求 110s 預算 一輪常跑不完 history；依賴多輪 P1 與手動同構：分 phase 排程
中 OpenAPI 雲端 RST 仍可能 TOP 更新可能停在舊交易日 監控 error=fetch_failed_kept_previous；必要時中轉
中 batch_run_log 主要在 chips 寫入 market-data／history 成果觀測不足 phase 級 log 或擴欄位
中 TOP20 進批次 → N 變大再變小 曾 ~35 檔；現 ~持股+20，仍重 history 可選「僅持股∪觀察」
中 MIS 與 Yahoo 量能口徑差 ~10% 即時量 vs 日線量 UI 標來源（已有部分 hint）
低 手動與 cron 同時跑 Storage 競態 夜班尖峰少連按
低 FOMC／總經「今日已掃」曾跳過新序列 0.6.45 已 force catalog 新增 FRED id 時回歸測
低 前端/Edge 雙部署 git push ≠ Edge；易以為已修 清單用 functions list sha

7.3 設計債（非立即 bug）

  • tradeValue 欄位在 TOP20 實際存成交股數（相容舊 JSON）—— review 時勿當成交金額。
  • 布林中軌 = SMA20，圖上與 MA20 重疊屬正常。
  • DEV self-hosted 與正式雲端網路環境不同，正式才是 OpenAPI RST 的主戰場。
  • Edge 無狀態：長任務只能 phase／多輪，不能當 job queue。

8. 觀察與建議（給大規模 review 用）

8.1 觀察（事實）

  • OpenAPI 只用在：TOP 名單、基本面估值／最新月季、部分融資借券備援、上市清單。
  • 最重的外網：rwd T86 大檔、MOPS 歷史、Yahoo 日線（標的數 × 是否 skip）。
  • 最脆的正式區路徑：雲端 → openapi.twse.com.tw；已用軟取用緩解，未消失。
  • 手動比 cron 可靠：分 job 各有時間預算；cron 受 60s pg_net + 110s 內建預算雙重限制。
  • 資料正確性多半「多輪收斂」而非「單次完整」——符合 P1。

8.2 建議優先序

#建議目的成本
1 正式區 pg_net timeout 調高（≥180s）或分 phase cron 觀測真實、少假紅燈 低（SQL alter_job）
2 cron 與手動同構：三個 generate-* action history 穩定補到 中
3 phase 級寫入 batch_run_log／admin 摘要 可解釋「卡在哪」 中
4 OpenAPI 失敗率告警（kept_previous 計數） TOP 過期可感知 低–中
5 history 可選「不含 TOP、僅持股∪觀察」 降 MOPS 成本 中
6 文件化「tradeValue=股數」於 SPEC 防後續 agent 誤用 低
Review 時不要做的假設： 「DEV 正常 = 正式正常」、「HTTP 200 = 資料最新」、「cron 失敗 = Edge 沒跑完」、 「沒打 OpenAPI = 不依賴證交所」（還有 rwd／MIS／MOPS）。

9. 建議驗證 Checklist

  • □ 左下角版本 ≥ 0.6.52；Edge stock-report ≥ v37
  • □ TOP20 重新整理：成功或 reused／備援，不應再裸 500 Connect RST
  • □ generate-history 單獨執行：即使 TOP 外網掛，仍應進入 MOPS（有 Storage 名單或至少持股）
  • □ generate-market-data 二次：摘要見 dailySkipped 高、秒數下降
  • □ 技術面：日 K + 均線 + 布林 + KD + 量
  • □ 抓取狀況：手動標「手動」；理解 cron 可能因 60s 顯示失敗但資料已寫
  • □ 週末看 TOP／籌碼資料日停在上交易日屬正常
