4. 風險評估

Supabase Cloud 546 / wall

  • 單 isolate 串 chips+daily+history 易 546 → 禁止併回 generate-all
  • cloud 約 ~150s wall；history 單輪 MOPS 大檔可能吃滿
  • 緩解：每 action 獨立 HTTP；錯開 ≥5 分鐘；持股少時較穩

pg_net / cron 延遲

  • cron 觸發 ≠ Edge 立刻跑完；高峰時 queue 可延數秒～數十秒
  • timeout_milliseconds 需足夠（現有 60s；history 若常踩線可提到 120s）
  • 同分鐘多 job 互搶 → 甘特上 chips 禁區勿重疊

資料窗 miss

  • BFI/T86 兩班可能雙 miss（來源晚）
  • 17:15 market-data 時 BWIBBU 可能尚未 18:00 → 靠 22:00 保險
  • 借券 22:30 更新晚於 21:45 → 當日可能不完整

history 12/12 速度

  • 一輪：月 ≤4、季 ≤2 → 季滿約需 6 輪
  • 一天 2 輪 ≈ 3 交易日近 12 季（優於完全無自動）
  • 新股仍可 warm / 手動加速

外部源限流 / 空回

  • Yahoo 空回不覆蓋既有 daily（0.6.50）
  • MOPS 大檔記憶體；MAX_BACKFILL_QUARTERS=2 是刻意保守
  • TWSE RST 等：market 短路、history 下輪再試

密操作 / 文案

  • job 必須分開命名，避免再以為 nightly=整包
  • 改線上用 cron.alter_job，勿重灌 secret
  • Admin dueBy / ACTION_SCOPE 同步

5. 建議落地順序

#動作風險驗收
1 新增 stock-report-market-data：17:15 + 22:00，action=generate-market-data 低 二次跑 dailySkipped/allCached 高
2 新增 stock-report-history：17:20 + 22:05，action=generate-history 中（wall） 持股 revenueMonths/profitQuarters 跨日增長
3 pg_net timeout 若 history 常 timeout → 該 job 調 90–120s net._http_response 非 null timeout
4 Admin 文案 + 時間軸 dueBy 排程表可讀、無「未解析」
5 （可選）觀測 1–2 週後再加深夜 chips 補洞 BFI/T86 命中率

6. 設計原則（摘要）

要做

  • phase 分開 HTTP（對齊 0.6.49 free tier）
  • market-data → +5m → history 順序
  • 主班對準來源窗；保險班對準晚到／第二輪
  • 齊了短路，多班成本可控

不要做

  • cron body 再塞回 generate-all 一把抓
  • 與 chips 同分鐘連打
  • 假設月營收「每天 21:00 統一更新」
  • unschedule+schedule 重寫 CRON_SECRET
