資料時序：點一個情境，看它怎麼走

上面那張分層圖說的是「東西擺在哪」，這一張說的是「一次請求依什麼順序經過它們」。 選一個情境，圖上會亮起該次呼叫實際走的路徑（節點上的圈號就是先後順序）， 下方列出每一步發生的時間點。

    02兩支 Edge Function

    sources/supabase/functions/ 底下只有這兩支，而且 兩支的 JWT 設定不一樣：

    函式線上 verify_jwt誰進得來版本（正式 / 測試）
    stock-pricetrue已登入的前端（帶 anon key + JWT）v12 / v8
    stock-reportfalsepg_cron（帶 x-cron-secret，不帶 JWT）＋ 前端的白名單呼叫v15 / v27
    repo 裡的部署指令與線上實況不一致

    sources/supabase/README.md 與根目錄 README.md 的部署段落， 對兩支都寫了 --no-verify-jwt；但實際線上（兩區都查過） stock-price 是 verify_jwt = true。 以 CLAUDE.md §13.3 的說法為準：stock-price 用預設即可， 只有 stock-report 一定要帶 --no-verify-jwt。 照 README 抄指令會把 stock-price 開成公開端點。

    反過來，stock-report 被重設成 true 的話盤後批次會全數 401 —— 而且不會有人發現，因為前端讀的是 Storage，畫面照樣有（舊）資料。

    03排程

    四個 pg_cron job 全部寫在 sources/supabase/schema.sql， 全部用 pg_net 打同一支 stock-report， 差別只在 body 的 action 與 timeout_milliseconds := 60000。 這個 repo 沒有 migrations/ 目錄 —— schema.sql 是手動套用的，而且明確標示不具冪等性。

    00 03 06 09 12 15 18 21 24
    stock-report-nightly
    */15 8-15 * * 1-5台北 16:00–23:45，每 15 分鐘一次 · 平日 · 32 次／日 → generate-all
    source-probe
    */15 8-15 * * 1-5與上者同拍，但走獨立觀測路徑，不會改到報告 → probe
    macro-daily
    0 13,15 * * *台北 21:00 / 23:00 · 每天（美國數據不看台股交易日）→ sync-macro
    fx-daily
    0 3,9 * * *台北 11:00 / 17:00 · 每天 · 刻意避開 macro-daily 的時段 → sync-fx

    時間軸為台北時間（UTC+8）。cron 表達式本身是 UTC。

    改排程不要重跑 §6c

    schema.sql 不具冪等性，重跑會多建一個同名 job。只改時間請用 cron.alter_job(jobid, schedule := '*/15 8-15 * * 1-5')。

    04一天 32 次為什麼不貴

    每 15 分鐘叫醒一次，但真正對外抓資料的次數遠少於 32。四道閘門依序把不必要的工作擋掉， 判斷邏輯全部是 pollPlan.ts 裡的純函式，並由測試釘住。 跨批次的狀態不另外開表，直接讀 batch_run_log 今天的最後一列（readLastRun()）。

    1
    decideSkip() 今天的 T86 已凍結 而且 今天的融資融券已到齊 → 這一輪什麼都不做。
    零次對外請求
    skip_reason = 'complete'
    2
    nextT86State() TWSE 從 16:00 起每 15 分鐘會改寫 T86。連續兩次指紋相同才判定為凍結 —— 只比對一次會把中途的暫時值當成定稿。
    t86_frozen 才允許收工
    3
    MAX_RUNS_PER_DAY = 40 硬上限。排程本身一天只會觸發 32 次，這 8 次的餘裕是留給手動觸發與重試的。
    超過即停
    skip_reason = 'run-cap'
    4
    runSignature() 把 {dataYmd, t86, margin, borrow, tickers} 壓成一個簽章。與上一輪相同就不重寫報告、也不清理舊檔。
    regenerated = false
    Storage 完全不動

    結果是：真正產生報告的通常只有盤後資料落地的那兩三輪，其餘二十幾輪在第一或第四道閘門就結束了。

    06資料庫

    九張表，全部在 sources/supabase/schema.sql。 RLS 的設計有三種模式，看懂這三種就懂整個權限模型：

    • 使用者隔離 —— auth.uid() = user_id，讀寫都限自己的列。
    • 前端唯讀 —— 只給 SELECT policy，沒有寫入 policy，所以只有 service role 寫得進去。
    • RLS 開但零 policy —— 任何一般使用者都碰不到，等於後端專用。
    表主要欄位RLS用途
    workspacesid · user_id · name
    UNIQUE (id, user_id)    		使用者隔離一個帳號可有多個工作區
    transactionstx_date · market · ticker · tx_type · price · qty · fee_tax使用者隔離複合外鍵 (workspace_id, user_id) 指向 workspaces，防止把交易掛到別人的工作區
    price_cachekey PK：TPE:2330 / US:AAPL / FX:USD前端唯讀三層價格快取的第二層
    stock_nameskey PK · name前端唯讀美股中英文名；台股中文名走 twlist
    user_settingsdefault_fee_rate 預設 0.001425 · theme使用者隔離舊的 ai_* 欄位已 DROP，改放 app_settings
    app_settingsid CHECK (id = 1) 單列
    ai_provider · ai_base_url · ai_model · ai_api_key    		全體可讀
    只有 admin 可寫    		AI 設定全站共用。API key 是明文，而且會傳到瀏覽器（見 §09）
    chip_raw_cachePK (ymd, dataset) · payload JSONB零 policy原始回應快取，保留 14 天
    batch_run_logtaipei_ymd · runs_today · skipped · skip_reason · run_sig · t86_fingerprint · t86_frozen …零 policy同時是批次的跨輪狀態儲存，不只是日誌
    source_probe_logbwibbu_ok/date/fp/rows · borrow_ok/date/fp/rows零 policy與批次分離的資料源觀測
    batch_run_log.macro_synced 已停用

    自 0.6.5-dev.2 起永遠是 NULL —— 總經同步被拆成獨立的 macro-daily 排程後，這個欄位就沒人寫了。看到 NULL 不是故障。

    07Storage

    只有一個 bucket reports，public = true： 任何人拿到 URL 都讀得到，只有 service role 寫得進去。 前端因此可以完全不經過 Edge Function 取得報告 —— 這是整個讀取路徑最便宜的部分。

    reports/ ├── manifest.json {ymd, dataDate, generatedAt} — 先讀它才知道要去哪個資料夾 ├── 20260728/ │ ├── 2330.json 盤後籌碼報告 schema 2，約 5KB │ ├── 2454.json │ └── … 只留 7 天，pruneStorage() 用 /^\d{8}$/ 比對後刪除 ├── daily/2330.json schema 1 · rows:[[date,o,h,l,c,v]] 一年份 · 約 10.8KB · 覆寫不刪 ├── fundamental/2330.json schema 2 · 估值 + revenueMonths(12) + profitQuarters(8) + 產業別 ├── news/2330.json schema 1 · 最多 10 則標題 ├── macro/us.json schema 1 · 五項指標 × 12 個月 · 全站一份 └── fx/twd.json schema 1 · 八個幣別一年日線 · 全站一份
    uploadJson() 明確設定 cacheControl: '0'

    supabase-js 的預設是 3600 秒。0.6.4-dev.5 因此發生過線上事故： 瀏覽器拿到一小時前的舊資料，連 Ctrl+Shift+R 都救不回來， 因為過期的是 CDN 那一層。這個 '0' 不能拿掉。

    報告：Storage 優先

    所有報告類資料都走 services/reportsBucket.ts 的 downloadReportsJson()：先 getPublicUrl(path)， 再用原生 fetch(url, { cache: 'no-store' }) —— 刻意不用 .download()。

    MIN_REPORT_SCHEMA = 2，其餘皆為 1。 當年用 === 造成過 0.4.0 的全面停機：後端 schema 一升版， 所有還沒重新整理的前端立刻判定資料不合法。

    09AI 分析

    位置在「個股分析 → AI 分析」分頁。這是整個系統唯一一條 不經過 Supabase 的對外路徑：瀏覽器直接打 AI 供應商，沒有 Edge Function 代理。

    瀏覽器 AiTab.tsx · aiClient.ts
    buildAiPayload()把技術指標、籌碼、基本面、新聞標題、總經組成一份 payload
    renderAiPrompt()輸出 {system, user} 兩段提示詞
    從 app_settings 讀 provider / base_url / model / api_key
    AI 供應商 兩條實作路徑
    google POST generativelanguage.googleapis.com/v1beta/models/{model}:generateContent
    header x-goog-api-key · role 是 model 不是 assistant · maxOutputTokens 8192 · thinkingConfig.thinkingBudget = 0
    收到 400 時，脫掉 thinkingConfig 重試一次
    openai-compatible POST {baseUrl}/chat/completions（Ollama / vLLM / 其它）· 選擇性 Authorization: Bearer
    帶相容欄位 max_tokens 8192 · reasoning_effort:'none' · think:false · chat_template_kwargs
    收到 400 時，整組相容欄位撤掉重試一次

    推理型模型的三段處理（0.6.9-dev.4）

    1
    請端點關掉思考送出 thinkingBudget / reasoning_effort / think 等欄位。有些端點會直接照做。
    最理想的情況
    2
    stripThinkTags()端點不理會、把思考塞進 content 時，把 <think>…</think> 剝掉。
    使用者看不到思考過程
    3
    改用 reasoning_content只有推理欄位、content 是空的時候，退而用它，但強制前置 REASONING_FALLBACK_NOTICE 警語。
    明示這是推理過程
    不是正式結論

    另外，回應被截斷時（finishReason: MAX_TOKENS 或 finish_reason: 'length'） 會附上 TRUNCATION_NOTICE。逾時 AI_TIMEOUT_MS = 180000， 涵蓋整個 body 讀取而不只是 headers。錯誤分成六類（auth / rate-limit / server / timeout / network / bad-response）， 不做任何自動重試 —— 每一次呼叫都是使用者在付錢。

    踩過的坑

    部署 stock-report 一定要帶 --no-verify-jwt

    兩區的 stock-report 都是 verify_jwt = false。被重設成 true， 盤後批次會全數 401 而且不會有人發現 —— 因為前端讀的是 Storage，畫面照樣有（舊）資料。 stock-price 則用預設即可。

    db query --linked 認的是「當下的工作目錄」

    2026-07-27 實際發生：functions download 把 cwd 留在暫存目錄， 之後一次「改測試區 cron」的 db query --linked 在那個沒有 link 設定的目錄下執行， CLI 退回全域設定，寫進了正式區。cron.schedule 照樣回傳成功， 緊接著的覆驗查詢也在同一個（錯的）資料庫裡，所以驗起來完全正確。

    對策：任何會寫入的查詢，把「專案身分欄位」放進同一次查詢裡 —— 例如 SELECT count(*) FROM batch_run_log（正式區 2、測試區 0）。 分兩次查擋不住這種錯，因為 cwd 可能在兩次之間被改掉。

    supabase link 有全域副作用

    不是 per-directory。在別的目錄重新 link 會把前一份清掉。 要查另一個專案時優先用支援 --project-ref 的指令 （functions list/deploy/download、secrets list）； 只有 db query --linked 沒有這個選項。

    稽核要用 functions download 逐檔比對

    不要看版本號推論。曾遇到版本號較新的那支反而是舊程式碼 （測試區 stock-price v2 落後 137 行、misParse.ts 根本沒部署上去）。 比對基準要對應分支：正式區比 main、測試區比 dev —— 拿錯基準會誤判「已同步」。

    manifest.json 日期落後時先確認星期

    cron 是 1-5，週末本來就不跑。週末看到日期停在週五是正確的，不是故障。

    0.6.8 與 0.6.9 都是純前端

    這兩版完全沒有動到 sources/supabase/。所以線上的 Edge Function 與 0.6.7 時期是同一份程式碼，稽核時可以直接跳過。
