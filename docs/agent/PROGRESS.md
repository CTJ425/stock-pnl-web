## 📅 Log: 2026-09-30 17:20:00 Asia/Taipei (Task 175 / BUG-087 當沖稅率對齊, 0.10.9)
- BUG-087 resolved, and the resolution is that **the engine was never wrong**. The user reported on 2026-09-30 that every figure now matches the broker app: 6560 at price 32.2 shows −587 / −1.8 in E.SUN, and the engine computes −587 / −1.80% / break-even 32.79 for the same holding (verified by running `estimateUnrealized` + `breakEvenPrice` against the real position, not by hand). −587 can only come from a 0.3% tax (0.15% would give −539), so the broker had gone back to the full rate overnight — exactly what the 現股當沖 hypothesis predicted and the only thing it predicted that needed no code change.
- The boundary is the **calendar day, not the 13:30 close**. The decisive detail was already in the record and had been read as mere timestamp noise: the 2026-09-29 E.SUN screenshot was taken at **14:46**, an hour after the close, and still showed 6560 at 0.15% (32,400 − 46 − 48) next to 2303 at 0.3%. So a "switch back after the close" rule — which is what the user first proposed — would have diverged from the app for 13:30–24:00 on the buy day.
- Told the user no detection, no cron and no column is needed: the rule is `lot.date === todayTaipei`, a pure derivation that flips by itself at midnight. Confirmed nothing persists an unrealized figure (no migration mentions it, no snapshot table), so there was nothing to migrate.
- Recommended, and built, the **narrow** version: only the 券商 / 牌告 caliber halves the tax. `HoldingRow.brokerUnrealized` already exists for exactly this purpose ("aligning with broker app", `holdingRows.ts`), and `pnlBasis.ts` already makes it a user-visible basis. The app's own `unrealized` and `breakEven` keep 0.3%, because the halving is conditional on actually day-trading and on eligibility this app cannot see (處置股 / 警示股 / 全額交割股 cannot be day-traded; the account needs a 當沖同意書). Break-even asks "what price covers cost if I *don't* sell today", so a conditional rate understates it.
- Implementation: `lotSellTaxRate(ticker, lotDate, today)` + `DAY_TRADE_TAX_SUNSET = '2027-12-31'` (`src/utils/pnlEngine.ts`); `estimateUnrealized` takes a 7th `dayTradeDate`, **passed in, never read from the clock** — an engine that calls `new Date()` makes the 78-tag historical recompute that cleared this repo impossible to repeat. `buildHoldingRows(…, today)` feeds it to the posted-rate call only, so `breakEvenPrice` is untouched and the closed-form-seed hazard I had flagged (a single `taxRate` seeding a bounded refinement loop, `fees.ts:256`) never had to be solved. The fallback lot for a hand-built `Holding` carries `date: ''`, which can never equal a calendar date.
- Labels, because a number that moves overnight with no trade behind it is unreadable: the 牌告 row in the expanded holding detail gains 「含今天買進的股票，證交稅以當沖 0.15% 估算」 (`HoldingRow.brokerDayTradeTax` → `.hl-method-note`), and 個股分析 gains 「券商以當沖稅率估」 with the full explanation on hover. `brokerDayTradeTax` is computed from the same `lotSellTaxRate` predicate the figure uses, so the label cannot claim a halving the arithmetic did not apply.
- Edge: `aggregateHoldings(ledgers, quotes, ymd, today)`. The fourth argument is the run's Taipei **calendar** date (`dashDate(taipeiYmd(deps.now()))`, already at both `holdingsRun.ts` call sites), deliberately not `ymd` — that one is the market day and points back at Friday on a weekend, which would halve a lot that survived the weekend. Only the posted-rate call reads it, so a 月退 workspace's main card figure follows and a 現折 one does not.

The regression tests pin the user's real numbers both ways — buy day 券商 −340 / net −389 / break-even 32.79, next day both −587 — plus: no `today` reproduces the old behaviour exactly, an older lot of the same ticker stays at 0.3%, ETF 0.1% → 0.05%, bond ETF stays 0, 2028 no longer halves, SHORT never halves. `npm run build`, `typecheck:edge`, `lint` exit 0.

## 📅 Log: 2026-09-30 16:05:30 Asia/Taipei (release tooling — ship/versioning moved out of this repo)
- User asked for `ship` and `versioning` to become reusable skills for other repos too, hosted in `script-docs` and installed over `curl`. Both are now **global** skills (`~/.claude/skills/`), and this repo's copies under `.claude/skills/` were deleted — `git rm`, so the old text is one `git show` away if the cutover has to be undone.
- Design: the skills hold the rules, this repo holds the paths. Everything project-specific now lives in **`.claude/release.config.json`** — three sections, each key owned by exactly one of them. `repo` (branches, `appDir`, changelog path, `changelogLang`) is shared; `version` (`syncFiles`, `release`) belongs to `versioning`; `ship` (`gates`, `flow`, `deploy`, `verify`, `record`) belongs to `ship`. Deploy is **not** a command string: `deploy.hookSkill` names `supabase-ops`, because "DEV is cloud not local docker" and `--no-verify-jwt` are paragraphs, not a `cmd`. ship is forbidden from inventing a deploy command and stops to ask instead.
- Two config facts worth keeping: `syncFiles` no longer lists `package-lock.json` as a JSON key — `sources/package.json` is `type: "npm"`, so `npm version --no-git-tag-version` updates the lockfile's `version` **and** `packages[""].version` together (editing one by hand leaves the other stale and `npm ci` then installs a number the app disagrees with). And `release.publishedBy` is `"ci"` here, because `release.yml` creates the Release on the `main` push; the skill only confirms and repairs it with `gh release edit` rather than racing the workflow.
- Verified on this repo before switching: `npm version 0.10.8 --no-git-tag-version --allow-same-version` in `sources/` leaves `git diff` empty, and all three `syncFiles` patterns match exactly once (`APP_VERSION = '0.10.8'`, `目前版本：0.10.8`). The config parses. Skills installed and visible to Claude Code as `ship` and `versioning`.
- `CLAUDE.md` § Release workflow / § Versioning shrank to the two facts a config cannot carry: a `main` push deploys no Edge/DDL, and `release.yml` skips an existing Release so the CHANGELOG must be final *before* the push (0.7.22).
- **Not yet exercised end to end.** The pipeline runs for real on the next release; if it misbehaves, the deleted project skills are recoverable from git. Nothing is committed yet — both repos are left dirty for review.
- _Update 2026-09-30 17:20:00_: this repo's side of the cutover was committed with 0.10.9 (see the entry above). `script-docs` is still uncommitted.
