# BUG-049 — Same-day BUY/SELL sort tie makes the engine report a false oversell

- Agent: Claude (main session)
- Status: SPEC
- Timestamp: 2026-09-04 15:10:00 Asia/Taipei

## Problem

PROD shows `2026-04-28 3037 賣出 50 股，但當時持有僅 0 股（超賣部分成本以 0 計算）`.
The database holds both legs: BUY 50 @840 (fee 59) and SELL 50 @915 (fee 202).

Both rows carry the **same** `tx_date` and the **same** `created_at`
(`2026-09-01 02:50:16.337075+00`) because one bulk import wrote them.

1. `dataProvider.ts:314-315` orders by `tx_date` then `created_at` only. Both keys tie.
2. PostgreSQL's sort is not stable, so PostgREST can return the SELL first. Proven: the
   same `ORDER BY tx_date, created_at` returned BUY-first in one query shape and
   SELL-first in another against the same PROD table.
3. `pnlEngine.ts:313` sorts on the same two keys. `Array.sort` is stable, so it keeps the
   SELL-first order.
4. `tx_nature` is `null`, so the day-trade pairing block (`pnlEngine.ts:418-428`) never
   runs. This is correct and must not change — `fee_tax = 202` is the full 0.003 tax rate,
   which proves these are two spot legs, not a day trade.
5. The SELL runs with `pos.qty === 0`, so it warns and takes a cost basis of 0.

Measured on the real 111-row PROD table: 3037 holds 250 shares instead of 200, realized
profit is 45,548 instead of 3,489, and total `realizedTw` is overstated by 42,059 TWD.
14 of the 15 same-day BUY/SELL pairs in that table are exposed to the same tie.

## Contract

Inputs and outputs of `computeLedger` do not change. Only the order in which it processes
transactions changes, and only when the existing keys tie.

Add a tie-break to the sort in `computeLedger`, applied **only after** `tx_date` and
`created_at` both compare equal:

1. The leg that **opens** a position sorts before the leg that **closes** it:
   - `tx_nature !== 'SHORT'` and `tx_type === 'BUY'` → open
   - `tx_nature === 'SHORT'` and `tx_type === 'SELL'` → open
   - every other combination → close
2. Then order by `id` so the result is fully deterministic.

Also add `.order('id', { ascending: true })` to the Supabase `listTransactions` query so
PostgREST itself returns a stable order.

### Must not change

- The day-trade pairing block, `splitFeeTax`, fee or tax maths, and every existing test.
- The relative order of any two transactions whose `tx_date` or `created_at` differ.
- The local (`localStorage`) provider's `listTransactions` — it already writes
  millisecond-incremented `created_at`, so it never ties.
